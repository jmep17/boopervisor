Boopervisor v1

A local web interface for reading and editing Claude Code's on-disk configuration — settings, skills, plugins and MCP servers — and nothing that lives behind an API.

TL;DR

Every ticket is built, reviewed and committed: 302 tests, typecheck, lint and next build green, and all five routes serving real configuration. The work that mattered was not writing the features but correcting them — four assumptions about Claude Code's own file formats turned out to be wrong, two of which wrote values Claude Code ignores.

Next → nothing outstanding; v1 is committed and the scope question is settled.

01

The catalog is hand-owned, not inferred

A research pass over the settings reference populates src/lib/catalog/: 217 keys across 19 topics, extracted deliberately and committed.

Why extraction rather than a schema

The reference is the only description of these keys that exists. Extraction scripts run on demand, never at build or runtime, and hand-written corrections live beside the generated JSON in overrides.ts — each with a note, so an unexplained override is distinguishable from a bug. See ADR 0003.

04

Settings show what Claude Code will actually do

Four files read and merged by precedence, each key showing its effective value, the scope that won, and what every scope contributed. Uncatalogued keys are surfaced, not hidden.

The nested-key defect

Fifty-nine of the 217 keys are nested — permissions.allow names a key inside permissions, not a top-level key with a dot in it. Both reading and writing treated them as flat, so nested settings never displayed and writing one produced a key Claude Code ignores. Both now address keys by path through paths.ts.

done
05

Every write goes through one path

mutateJsonFile takes a file, the snapshot it was composed against and a pure change: it validates, backs up, stale-checks by mtime and content hash, and logs.

Why generic rather than settings-specific

The same function writes the mcpServers key of ~/.claude.json while leaving the rest byte-identical, records item state, and performs restores. A settings-only version would have forced three more write paths, each with its own backup and staleness bugs.

06

The two keys that break silently get real editors

permissions as three ordered rule lists and hooks as entries driven by the hooks catalog, both refusing a malformed value before anything is written.

done
07

Items are one concept, three listings

/mcp, /skills and /plugins share a master-detail shape, one state store and one action. /history shows every mutation with a diff and restores any backup.

Disabling uses Claude Code’s own mechanism

Each item type has one settings key that disables it — deniedMcpServers, disabledMcpjsonServers, skillOverrides, enabledPlugins — so a disable merges by precedence like any other setting. Archival is Boopervisor’s own state, holds the item disabled, and moves no files. See ADR 0002.
