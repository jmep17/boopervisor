### Direction candidates from the frontend audit (not planned; available on request)

- **A theme choice (system / light / dark).** `globals.css:136-143` defines `.light` and
  `.dark` overrides and `docs/design-system.md:29` documents them, but nothing in the app
  ever sets either class — the switch exists in CSS only. A control in the header, persisted
  in a cookie the server layout reads (so the first paint has the right class and there is
  no flash), would deliver what the doc already describes. Trade-off: one more piece of
  Boopervisor-owned state; a cookie is fine for a local tool. Effort S.
- **Find-as-you-type on `/settings`.** 217 catalogued keys across 17 topics render on one
  page (`settings-list.tsx`) with no filter and no topic navigation. A `?q=` search param
  filtered server-side keeps the "state lives in the URL" convention and needs no client
  state; a sticky topic list would be the alternative. Trade-off: a filtered list must still
  show the "Settings files" section and the Uncatalogued section, or say why they are
  hidden. Effort S–M.
- **Wide-screen density on `/settings`.** At the 72rem container a row puts its key at the
  far left and its value at the far right; scanning is a long eye travel. Options: cap the
  list at `max-w-4xl`, or move the value beside the key with the badge trailing. This is a
  design call, not a bug; plan 008 fixes the overflow without choosing. Effort S.

### Frontend findings considered and rejected

- Touch-target sizes (`Checkbox` is 16px, the dialog close button 24px; WCAG 2.5.8 wants
  24px) — a desktop-local tool used with a pointer; not worth a plan.
- `prefers-reduced-motion` — the only motion is `transition-colors` and the switch thumb's
  transform; nothing to reduce.
- A skip-to-content link — five nav links; not worth it.
- A hamburger menu for the header — five short links wrap; plan 010 says not to add menu state.
- A theme toggle as a _fix_ — nothing is broken; the app follows the OS. Recorded as a direction candidate above.
- Replacing `<details>/<summary>` rows with a component — native disclosure is accessible,
  keyboard-operable and needs no client state; keep it.

### Observed outside this audit's focus (not planned)

- **Writes fail under a plain `next dev` / `bun dev` on Node (2026-09-01, execute-review find).**
  `src/lib/config/mutate.ts:181` and `src/components/history/history-list.tsx:27` call
  `Bun.file(...)`. `bun run dev` executes the `next` bin under Node (bun honours its shebang
  without `--bun`), so every Save fails with `Bun is not defined`. Reviewer reproduced it in a
  worktree and confirmed writes work under `bun --bun run dev`. Fix is small: use `node:fs`
  `access`/`existsSync` in both places, or document `bun --bun`. Pre-existing on `main` at
  `484309b`; not introduced by plans 003–006. **Fixed by plan 012, merged 2026-09-01** (`exists()`
  in `mutate.ts` using `node:fs/promises` `access`; browser-verified under plain `bun run dev`).

- `src/components/history/history-row.tsx:4` imports `basename` from `node:path` inside a
  `"use client"` component. It typechecks and lints, and Next bundles a polyfill, but it is
  the only Node import in a client file; a `record.path.split("/").pop()` would remove the
  dependency. Correctness/hygiene, not design — noted for a future correctness pass.

## Findings considered and rejected

- Anthropic Admin API section — explicitly out of scope in `docs/PLAN.md` (different product, different authentication).
- Watching files for external changes — `docs/PLAN.md`: "a single-user local tool does not earn the machinery"; stale-write detection covers the risk.
- Physical archival (moving item files) — rejected by ADR 0002.
- Shelling out to the `claude` CLI for writes — rejected by ADR 0001; the CLI has `plugin install/enable/disable` and `mcp add/remove` but no `config get/set`, and Boopervisor's preview/backup/stale-check would be unreachable through it.
- Editing SKILL.md / plugin.json contents — out of scope in `docs/PLAN.md`.
- Permission-rule evaluation-order warning — already implemented: the lists are titled "Deny (checked first)", "Ask (checked second)", "Allow (checked last)" in `src/components/settings/controls/permission-rules.tsx`.
- Validating against an official settings JSON Schema — none is published (checked settings-reference.md, 2026-08-30).
- Authentication for the local server — binding to localhost (plan 003) is the right size for a single-user tool; a token would add friction without a threat it addresses.
